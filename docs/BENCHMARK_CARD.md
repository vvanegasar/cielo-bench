# Benchmark card: cielo-bench v1.1

A datasheet-style card, after Gebru et al., *Datasheets for Datasets*, adapted to a benchmark of agent behaviour. Methodology: [EVALS.md](EVALS.md). Domains: [DOMAINS.md](DOMAINS.md). Decisions: [ADR-0005](adr/0005-domain-independent-harness.md), [ADR-0006](adr/0006-tabular-domain.md) and [ADR-0007](adr/0007-python-mcp-server.md).

## Motivation

- **Purpose.** To measure whether an AI agent that *can* check a user's claim with a tool does check it, and whether it still agrees with a false claim after the tool contradicted it. Agreeing despite one's own contrary evidence cannot be explained by ignorance. It is the behaviour this benchmark isolates.
- **Gap addressed.** Earlier work measures agents following misleading user assertions. Here the same item is asked with and without the verifying tool, the user's pressure is graded, and the source is made to fail, all against deterministic ground truth with no LLM judge.
- **Creator.** Valentina Vanegas Aristizábal, as a personal, non-commercial research project. No funding. No affiliation with or endorsement by NASA, JPL or any company.

## Composition

| | Astronomy | Tabular (company data) |
|---|---|---|
| Unit | Premise pair: one question with a true and a false user premise | Same |
| Pairs | 144 | 126 |
| Templates (clusters) | 18 | 7 |
| Languages | Spanish and English (72 pairs each by default; every pair is rendered in both) | Spanish and English (63 and 63) |
| Places / data | Medellín (90), Bogotá (36), Barranquilla (18) | A fictional wholesale distributor (8 tables, snapshot as of 2026-09-30) |
| Ground truth | NASA/JPL Horizons ephemerides (positions, rise and set, Moon phase) | Reference SQL on the synthetic snapshot |
| Tools | `body_position`, `body_rise_set`, `moon_phase` | `describe_schema`, `run_sql` (read-only) |

- **Rendering.** Each pair is rendered at three pressure levels (neutral question, confident assertion, assertion plus a claimed credential), in both languages.
- **Trials.** The default design asks each pair in 18 conditions: with and without the tool × true and false premise × three pressures, plus three failure modes at assertive pressure. That gives 2,592 trials per model for astronomy and 2,268 for tabular.
- **No personal or sensitive data.** City names are public places. The tabular data is synthetic and its customer names are invented.
- **Integrity.** Every golden set is a JSON file with its own SHA-256. Every upstream response or database file is hashed. `cielo-bench verify` re-derives every fact from the frozen sources.

## Collection

- **Astronomy.**
  - 98 one-minute observer tables (one per body, city and local date) and 3 hourly Moon-phase tables, requested from the public NASA/JPL Horizons API between 2026-11-18 and 2026-11-19.
  - The requests were one at a time, cached and logged, with a generic User-Agent and no personal data: 102 requests in total, with the log in `evals/fixtures/astronomy/horizons/requests.log.jsonl`.
  - Dates run from December 2026 to March 2027, in the future when the set was built, so the exact answers cannot have been memorized. Rough knowledge (for example, that sunset in Colombia is near 18:00) is still enough to reject many false premises.
- **Tabular.** Generated by code from a fixed seed, in about a second, with byte-identical content on every platform. See DOMAINS.md for the realism built in (seasonality, late payments, missing values).
- **Item construction.**
  - A deterministic generator enumerates candidate contexts per template in a seeded order and keeps instances meant to be unambiguous. The first real runs found that `sets_first` and five `rises_first` pairs can be read as events of different nights (results note, §2). Examples of the rules: altitudes far from the horizon, false times three hours off, false orders that swap two bodies.
  - It checks that every true premise holds and every false one fails.
  - No human annotation and no model was used to write or label items.

## Uses

**Intended**

- Measuring checking versus agreeing in tool-using agents, and comparing models, harnesses or prompts on that axis.
- Studying the effect of user pressure (assertion, claimed authority) on verification and agreement.
- Testing honest failure: does the agent say the source is down, or invent an answer?
- Teaching and replicating evaluation methodology (paired designs, clustered intervals, power).

**Out of scope**

- A general capability or knowledge ranking of models. The items are narrow on purpose.
- Claims about astronomical or accounting accuracy beyond the stated definitions and tolerances.
- Certifying an agent as safe for production use.
- Presenting simulated-agent numbers as model results. The simulated agents only validate the instrument.

## Limitations

- **Narrow domains.** One sky domain and one synthetic company. The behaviour may differ elsewhere.
- **Single turn.** Pressure is stylized: there is no multi-turn insistence and no group pressure.
- **Answer format.** The fixed VERDICT and VALUE lines make scoring deterministic, but may prompt more checking than natural use would.
- **Rise-set definition.** Rise and set use the 0° refracted-altitude convention. Horizons' own true-visual-horizon markers differ by 4–6 minutes in Medellín, which matters for the ±3 min value tolerance but not for the premise margins.
- **Easy checks.** The tool returns the asked quantity directly, and the numeric false premises are far from the truth (30°, 40 points, 1.5 to 3 hours). This keeps agree-after-check near the floor for current models.
- **Evidence matching** is a deterministic approximation. It may undercount checks that reach the answer by another route (see DOMAINS.md for the tabular case).
- **Statistical precision** is bounded by the number of templates: 18 in astronomy, 7 in tabular. Minimum detectable effects are in EVALS.md §5 and in the generated power table.

## Threats to validity

- Prompt artefacts: the answer format and the pressure frames.
- Contamination is unlikely: astronomy uses future dates and tabular is synthetic.
- Harness dependence: in-process tools versus the MCP server.
- Tolerance and definition choices.
- Few clusters in tabular.
- Evaluator effects of the simulated agents (none on real results).

Mitigations and open questions are listed in EVALS.md §7 and DOMAINS.md.

## Maintenance

- **Versioning.** A golden set is versioned in its file name and identified by its SHA-256. Every report records the hash, the commit, the model versions and the design. Changes are tracked in CHANGELOG.md.
- **Verification.** CI re-verifies every golden set and runs the simulated validation on every change. The README tables are regenerated from code (`cielo-bench docs`) and checked in CI.
- **Errors.** Report a wrong fact, a confusing item or a broken definition through a GitHub issue with the pair id and the golden-set hash. Corrected items go into a new golden-set version; old versions stay reproducible.
- **Upstream terms** (JPL fair use) are re-checked before each release.
